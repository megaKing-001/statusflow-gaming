
# STATUSFLOW GAMING — DEVELOPMENT RULES

## 1. Purpose

This document defines the development rules for StatusFlow Gaming.

These rules exist to keep the project:

- secure
- maintainable
- consistent
- easy to debug
- resistant to cheating
- compatible with the existing StatusFlow ecosystem

All future development should follow these rules unless a deliberate architectural decision changes them.

---

# 2. Source of Truth

The GitHub repository is the source of truth for application code.

The Supabase project is the source of truth for live database state.

Project documentation files explain the intended architecture.

Never assume that an old conversation, generated code, or AI response represents the current state of the project.

Before making major changes:

1. Inspect the current repository.
2. Inspect the relevant Supabase database objects.
3. Understand the existing implementation.
4. Make the smallest safe change.
5. Test the change.
6. Commit the change.

---

# 3. Never Guess Existing Code

Do not invent files, functions, tables, columns, components, or APIs when the existing project can be inspected.

If a file is referenced by another file:

- verify that it exists
- inspect its exports
- inspect its implementation
- verify its import path

Example:

If code contains:

```typescript
import { createClient } from '@/lib/supabase/server';

do not create a new server client blindly.

First verify whether:

lib/supabase/server.ts

already exists.


---

4. Preserve Working Features

Do not rewrite working systems unnecessarily.

When implementing a new feature:

1. Understand the existing feature.


2. Identify the smallest required change.


3. Avoid unrelated refactoring.


4. Test existing functionality afterward.



Do not replace the entire application simply because a new feature is being added.


---

5. Full-File Changes

When a file requires substantial modification, provide the complete replacement file rather than scattered patches whenever practical.

The replacement must preserve unrelated working functionality.

Never tell the developer to delete working code without understanding what it does.


---

6. Security First

Security is more important than convenience.

Never trust:

client-submitted balances

client-submitted rewards

client-submitted winners

client-submitted prices

client-submitted user IDs

client-submitted match results

client-submitted game outcomes


The server/database must validate sensitive operations.


---

7. Server Authority

The browser is an untrusted environment.

The client may request:

Play game
Start session
Submit action
Claim reward
Purchase item
Join match

The server must decide whether the request is valid.

Conceptually:

Client
  |
  | Request
  v
Server
  |
  | Validate
  v
Database
  |
  | Commit
  v
Result


---

8. Never Trust Client Rewards

Never accept a request such as:

{
  "reward": 5000
}

as proof that the user earned 5,000 SFP.

The server must calculate the reward from trusted game/session state.


---

9. Wallet Protection

Wallet balances are sensitive financial-like data.

Never allow a normal client component to directly modify:

sfp_balance

or equivalent wallet fields.

Balance-changing operations must go through trusted server/database logic.


---

10. Ledger First

Every balance-changing event must have an auditable reason.

Examples:

GAME_REWARD
DAILY_REWARD
REFERRAL_REWARD
STORE_PURCHASE
ADMIN_ADJUSTMENT
TOURNAMENT_REWARD

The exact transaction types should match the actual database architecture.


---

11. Idempotency

Any operation capable of changing a wallet must be safe against repeated requests.

Example:

POST /settle-session

If the same session is submitted five times, it must not pay five times.

Expected behavior:

First request  -> settlement succeeds
Second request -> already settled
Third request  -> already settled


---

12. Game Session Security

Every game should have a server-controlled session.

A session should have a lifecycle such as:

CREATED
STARTED
IN_PROGRESS
COMPLETED
SETTLED

A settled session must not be settled again.


---

13. Anti-Cheat

Games must assume that users can inspect and modify browser JavaScript.

Therefore:

do not put secrets in client code

do not expose authoritative answers unnecessarily

do not calculate final rewards only in JavaScript

do not trust client timers for important validation

do not trust client-generated random results

validate important actions on the server



---

14. Randomness

For games involving randomness, the authoritative result must be generated by trusted server-side logic.

The browser should not determine:

winning card
wheel result
crash point
football result
jackpot

unless the architecture explicitly uses a verifiable randomness mechanism.


---

15. StatusCrash

StatusCrash must not allow the client to determine the crash point.

The authoritative sequence should be conceptually:

Create round
     |
Generate trusted outcome
     |
Players interact
     |
Validate cash-out
     |
Settle

Do not move authoritative outcome generation into client JavaScript merely for convenience.


---

16. StatusWheel

The client should request a spin.

The server should determine the result.

Do not allow the client to submit:

selectedSegment = JACKPOT

and receive the jackpot automatically.


---

17. StatusCards

The server must control the authoritative card outcome.

Client-side animations may visually represent the result, but the client must not decide the result.


---

18. StatusQuiz

Important quiz information should not be unnecessarily exposed to the browser.

Where possible:

retrieve only information required for gameplay

validate answers server-side

calculate rewards server-side

prevent repeated settlement



---

19. StatusFootball

StatusFootball is a server-authoritative game.

Important game state must not depend solely on the browser.

For PvP:

players must be authenticated

match ownership must be verified

stakes must be validated

opponents must be verified

match state must be controlled

settlement must be idempotent

winner determination must be authoritative



---

20. PvP Security

A user must never be able to:

join as another user

change the opponent

change the stake after locking

declare themselves the winner

settle the same match twice

modify another player's match

create a fake payout


All such operations must be validated.


---

21. Authorization

Authentication answers:

Who are you?

Authorization answers:

Are you allowed to do this?

Always perform authorization checks for sensitive operations.

Being logged in does not automatically mean the user can modify every record.


---

22. Row Level Security

Do not disable Supabase RLS simply because a query fails.

If RLS blocks an operation:

1. Determine why.


2. Determine whether the operation should actually be allowed.


3. Fix the policy or trusted server flow.


4. Test again.



Never solve security problems by making every table publicly writable.


---

23. Secrets

Never commit secrets to GitHub.

Never place these in client-side code:

Supabase service-role key

private API keys

payment secrets

webhook secrets

encryption keys

signing secrets


Never use:

NEXT_PUBLIC_

for a secret.


---

24. Environment Variables

Environment variables should be used for configuration and secrets.

Public browser-safe variables may use:

NEXT_PUBLIC_

Private variables must not use that prefix.

If an environment variable is missing, fail clearly rather than silently using a fake value.


---

25. Error Handling

Errors should be handled deliberately.

Do not expose:

database internals

secret values

API keys

stack traces

sensitive user information


to normal users.

Log useful diagnostic information on the server where appropriate.


---

26. Loading and Failure States

Every important asynchronous feature should consider:

loading

success

failure

retry

empty state


Do not leave users staring at a blank screen when an API/database request fails.


---

27. Supabase Client Usage

Use the correct Supabase client for the execution environment.

Browser/client components should use the browser client.

Server-side operations should use the server-side client or trusted database mechanism appropriate to the project.

Do not expose server-only credentials to client components.


---

28. Next.js Rules

Follow the existing Next.js architecture.

Before adding 'use client', determine whether the component actually requires browser functionality.

Prefer server components where appropriate.

Use client components for functionality that requires:

React state

browser APIs

event handlers

client-side subscriptions


Do not convert the entire application to client components unnecessarily.


---

29. Imports

Use consistent import paths.

The project uses the @/* alias.

Example:

import Navbar from '@/components/Navbar';

or:

import { Navbar } from '@/components/Navbar';

The import must match the actual export.

Before changing an import, inspect the target file.


---

30. TypeScript

Do not introduce unnecessary any types.

Prefer explicit types for:

database records

game state

wallet transactions

API responses

match state


If the Supabase schema changes, update the relevant types where appropriate.


---

31. Database Changes

Never make application code depend on a database change that has not been applied.

For schema changes:

1. Create a migration where appropriate.


2. Apply it to the correct Supabase project.


3. Verify the result.


4. Update DATABASE.md.


5. Test affected functionality.


6. Commit the migration.




---

32. Existing Database Functions

Before modifying a database function:

1. Retrieve its current definition.


2. Understand its callers.


3. Identify dependent tables/triggers.


4. Check security implications.


5. Modify carefully.


6. Test both success and failure cases.



Do not replace database functions blindly.


---

33. Payment Systems

Payment integrations must be treated as security-sensitive.

Never trust the browser to confirm payment success.

Payment confirmation should come from a trusted provider/webhook flow.

Do not credit SFP merely because the browser says:

payment = successful


---

34. Currency Separation

Keep currencies conceptually separate.

Examples:

SFP
NGN
USD

Do not mix currency values without an explicit conversion rule.

Never assume:

1 SFP = ₦1

unless the current business rules explicitly define that relationship.


---

35. Game Economy

Game rewards must be economically controlled.

Before changing rewards, consider:

maximum daily issuance

average user earnings

abuse potential

treasury/platform exposure

payout liability

upgrade multipliers

tournament rewards


Never increase rewards blindly.


---

36. Testing

Every significant change should be tested.

At minimum test:

Normal user
Unauthorized user
Invalid input
Repeated request
Insufficient balance
Expired session
Already-settled session
Network failure
Database failure

For PvP features, test with two separate authenticated accounts.


---

37. Local Development

The project can be developed locally using Next.js.

The current Android/Termux environment has an important limitation:

Next.js Turbopack native bindings are not available on Android ARM64.

Therefore local development should use Webpack:

npm run dev -- --webpack

Do not assume:

npm run dev

will work correctly on Android.


---

38. Android Development

The current development environment may be:

Android phone
Termux
Node.js
npm
Git
Next.js
Webpack

When giving terminal instructions:

provide commands one at a time where practical

explain what each command does

avoid unnecessary complexity

do not assume a desktop environment

verify the current directory before destructive commands



---

39. Git Workflow

Before major changes:

git status

After changes:

git diff

Then commit meaningful changes.

Example:

git add .
git commit -m "Describe the change"
git push

Do not commit secrets.


---

40. Small Commits

Prefer focused commits.

Good:

Add football PvP matchmaking
Fix wallet settlement idempotency
Add daily reward validation
Fix Supabase server client

Avoid giant commits containing unrelated changes.


---

41. Do Not Rewrite Working Architecture Without Reason

AI-generated code can introduce unnecessary architecture changes.

Before accepting a large rewrite, ask:

What problem does this solve?

What existing behavior does it change?

What dependencies does it affect?

Can the same result be achieved with a smaller change?


Prefer the safer solution.


---

42. AI Coding Rule

AI assistants are development tools, not the source of truth.

Claude, Gemini, ChatGPT, or another AI may generate incorrect code.

Generated code must be:

1. inspected


2. compared with the existing architecture


3. tested


4. checked for security


5. checked against the real database



Never assume AI-generated code is correct because it compiles.


---

43. Preserve Project Documentation

Before making major architectural changes, update the relevant documentation.

Important documents:

PROJECT_CONTEXT.md
CURRENT_STATUS.md
ARCHITECTURE.md
DATABASE.md
DEVELOPMENT_RULES.md

These documents should remain synchronized with the project.


---

44. Debugging Rule

When an error occurs:

1. Read the complete error.


2. Identify the first meaningful error.


3. Locate the affected file.


4. Inspect the surrounding code.


5. Check dependencies/imports.


6. Check environment variables if relevant.


7. Check the database if relevant.


8. Make one controlled fix.


9. Test again.



Do not randomly change multiple files.


---

45. Build Before Production

Before deploying a major change, run:

npm run build

Fix build errors before considering the change complete.

Development mode working does not automatically mean production build will work.


---

46. Production Safety

Before production:

remove debug code

verify environment variables

verify RLS

verify authentication

verify wallet protection

verify payment verification

test duplicate requests

test unauthorized requests

test game settlement

test PvP settlement

inspect logs



---

47. No Silent Security Downgrades

Never make a security control weaker simply to make a feature work.

Examples:

Do not:

disable RLS
expose service-role key
trust client reward
trust client winner
remove authorization
make wallet writable from browser

without a documented, reviewed architectural reason.


---

48. Performance

Do not optimize blindly.

First identify the actual bottleneck.

Avoid:

unnecessary database requests

unnecessary realtime subscriptions

repeated authentication requests

fetching entire tables

unnecessarily large client bundles


Performance improvements must not weaken security.


---

49. Mobile Compatibility

StatusFlow Gaming should work well on mobile devices.

UI should account for:

touch input

small screens

slow connections

loading states

readable text

accessible buttons


Do not build interactions that require a mouse when a touch-friendly alternative is practical.


---

50. Final Development Principle

The project should follow this hierarchy:

Security
   ↓
Correctness
   ↓
Data integrity
   ↓
Reliability
   ↓
Performance
   ↓
User experience
   ↓
Convenience

Convenience must never override security or correctness.


---

51. Golden Rule

When unsure:

DO NOT GUESS.

Inspect the existing code.

Inspect the real database.

Understand the dependency.

Make the smallest safe change.

Test it.

Document it.

Commit it.

Then continue.
